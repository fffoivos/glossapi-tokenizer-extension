# operational_workarounds — experiment-local adapters for live allocations

> **In one line:** the deviations, kept visible: 34 small adapters written while GPU allocations were already held, each one narrowing a gap between the frozen scientific payload and what Slurm would actually let it do — and each one filed upstream as an issue rather than smuggled into the main path.
> **Period:** 2026-08-19 → 2026-08-23 (nine files committed on 08-22/23 in `a9ffa35b` … `0f7fc810`; the rest recovered on 2026-09-01 in `2aec4a66`). **Status:** complete; superseded upstream where the canonical runner adopted the fix.

## Why this existed

The rule for this study was to reuse the canonical `apertus-cscs-efficiency` runner unmodified, and to treat any gap as an issue first and a `workaround_*` in this tree second ([`../HARD_H2G_FULL_PANEL_SCORING_AND_NO_DECAY_BRANCH_PLAN_20260822.md`](../HARD_H2G_FULL_PANEL_SCORING_AND_NO_DECAY_BRANCH_PLAN_20260822.md), "Process and authority"). Almost every file here exists because a *held* allocation — scarce, already granted, ticking — could not be released while a packaging or topology mismatch was fixed properly upstream.

## What is here, and what it was for

- **Running inside an adopted allocation.** `run_in_existing_allocation_3140780.sh`, `launch_8b_s4_in_no_shell_allocation_3140780.sh`, `launch_direct_v15_*` and `run_1p5b_s4_direct_shell_3145729.sh` adapt the frozen S4/S5 segment launches to `salloc --no-shell` allocations that were already granted. `srun_node_gpu_visibility_v2.sh` fixes the matching GPU-visibility problem: an allocation requested as four one-GPU tasks per node inherits `gres/gpu:per_task:1`, but the canonical torchrun path starts one controller per node, which must own all four local GPUs. The flags were probed on both nodes of allocation `3141832`.
- **Phase-3 extension.** `run_1p5b_phase3_smoke_in_live_salloc*.sh`, `freeze_joint_pre_extension_gate_v14.sh`, `finalize_1p5b_phase3_smoke_v14.sh`, `prepare_update3456_transition_debug_v1.sh`, `postprocess_direct_v15_update3456.sh` and `launch_update3456_smoke_in_allocation_v1.sh` carry the 3,218 → 3,456 → 3,694 extension through its gates without re-running training.
- **Trajectory and full-panel scoring.** `export_greekmmlu_trajectory_checkpoints_in_allocation.sh` and `run_greekmmlu_trajectory_in_allocation.sh` convert and score the frozen checkpoint table inside one held GPU allocation; `run_legacy_bf16_three_checkpoint_matrix.sh` runs the pinned legacy evaluator over updates 2,618/3,218/3,694; `launch_parallel_stable_endpoint_scores.sh` plus the `checkpoint_*_stable_peak.tsv` manifests launch the two independent endpoint exports/scores concurrently inside the released 16-node allocation — operational bin-packing after training, with disjoint result roots and unchanged scorer inputs.
- **Repairs that must not rerun training.** `finalize_completed_stable_checkpoint.py` repairs post-save campaign receipts after the frozen post-save launcher invoked `/usr/bin/python3.11` outside the PyTorch uenv and could not import `torch`; `run_in_allocation_postprocess_recovery_compat.py` bridges an audited recovery permit into the older V99 runner; `archive_zero_update_s3_attempts.py` archives three checkpoint-free S3 launch failures; `workaround_holder_profile_time_bound.py` overrides only a stale in-memory holder timing (a promoted two-node 1.5B manifest had kept the one-node 33,967-second handoff estimate).

## Outcome

- Each pattern here became an upstream issue against `fffoivos/apertus-cscs-efficiency`: #137 (directory-valued scientific inputs as `required_env`), #146 with PR #148 (adopted controllers must propagate scheduler-complete geometry; direct execution should inject its manifest/code-root environment; retry-scoped receipts need an attempt nonce), #149 (ETA must include the every-25-update validation pass), #150 (post-training bin-packing), #151 (the implicit post-save runtime contract), #152 (full consumer-geometry compilation), plus evidence added to #61 and #88.
- The rank-zero-controller-plus-peer-holder wrapper was upstreamed as commit `1a0d672` in the efficiency repository.
- One class of failure is deliberately preserved rather than fixed: checkpoint *conversion* could not be made concurrent, because independent result roots do not stop two converters from contending on shared Megatron fused-kernel/NCCL initialization (`ncclInvalidUsage`). Conversion was serialized; only scoring is packed concurrently.
