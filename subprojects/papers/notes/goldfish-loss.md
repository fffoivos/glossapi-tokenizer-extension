# The Goldfish Loss: Mitigating Memorization in Generative LLMs (Hans et al., arXiv:2406.10209, NeurIPS 2024)

**Source:** arXiv:2406.10209  |  **Topic:** Loss  |  `txt/goldfish-loss.txt`, `pdf/goldfish-loss.pdf`

**TL;DR.** A drop-in modification to next-token training that pseudo-randomly excludes a 1/k subset of tokens (via a localized h-gram hash) from the loss, sharply reducing extractable verbatim memorization with only marginal degradation on downstream benchmarks — at the cost of needing more forward-pass tokens to reach loss parity.

## Key load-bearing facts
- Mechanism: forward pass runs on all tokens; the loss excludes a pseudo-random 1/k subset of tokens, so the model never learns to reproduce dropped tokens and diverges from the training sequence at inference (Abstract; Sec 1, lines 45-51; Sec 3, lines 234-250). The hyperparameter is the drop frequency k.
- Default/tested settings: the paper's running default is k=4 (lines 166-167). The full sweep of k values tested is {3, 4, 8, 12, 32, 128} (Figures 3/5/7/8, lines 377-386, 710-725, 922). There is NO k=50 anywhere in the paper.
- Localized hashed mask (Sec 3.1, lines 341-398): mask token x_i iff a hash of the h preceding tokens < 1/k. h is the hash context width, a SEPARATE knob from k. This guarantees identical masking of duplicated passages (defeats the leak-via-inconsistent-masking failure mode of static masks).
- h selection guidance: h must not be too small (h=7 given as a BAD example where the model fails to learn legitimate completions, line 346) nor too large (hash under-determined for the first h-1 tokens, line 350). The paper recommends/uses h=13, motivated by the 13-gram contamination-overlap convention of Brown et al. 2020 / Du et al. 2022 (lines 393-395). Experiments report Hash h=4 and Hash h=13 (lines 1214-1216). No h=50 anywhere.
- Memorization results: extreme setup (LLaMA-2-7B, 100 epochs on 100 Wikipedia articles): standard loss memorizes 84/100 verbatim, k=4 goldfish memorizes 0/100 (lines 421-425). Standard setup (1.1B TinyLLaMA-style, 20B tokens, 2000 canary docs repeated 50x): k=3/k=4 RougeL distribution overlaps the oblivious control (lines 436-451).
- Downstream benchmark impact: 'only marginal change' vs standard loss across Open LLM Leaderboard tasks (WinoGrande, PIQA, OpenBookQA, HellaSwag, BoolQ, ARC-E, ARC-C) for k=3 and k=4; 'no systematic differences' (Fig 3 caption lines 388-391; Sec 5.1 lines 643-652). The one exception (BoolQ) is a data-coverage artifact, not a goldfish effect.
- Key caveat the abstract hides — NOT a free lunch (Sec 5.2, lines 657-690): because (1 - 1/k) x input_tokens = supervised_tokens, goldfish supervises on fewer tokens. To reach validation-loss parity you must feed MORE input tokens (e.g. 26.7B input for 20B supervised at k=4) via more steps or larger batch. Authors explicitly state 'this is not a free lunch' (line 690) and recommend rescaling the world batch size by the same formula.
- Scope of validation: models are 1B-1.1B and 7B params, 20B-token scale, single-epoch RedPajama + repeated canaries; English only. Scaling to tens/hundreds of billions of params is flagged as an open question (lines 930-932). Conclusion suggests selective application (late-curriculum or high-risk sources only) and notes 'higher masking rates than those explored in this paper' may suit low-entropy text like code (lines 938-943).

## Citation audit — what CURRENT_HYPERPARAMETERS.md cites this for

**Claim:** The Goldfish loss suppresses verbatim recall with little downstream-performance impact.
**Verdict:** `PARTIAL`
**Evidence:** The memorization-suppression half is strongly supported: 'significant reductions in extractable memorization' (Abstract, line 25); k=4 memorizes 0/100 articles vs 84/100 for standard loss (lines 424-425). The downstream half is supported for the TESTED settings: 'we note only marginal change in performance for models trained with goldfish loss (k = 3 and k = 4)' (Fig 3 caption, lines 389-391) and 'no systematic differences' (Sec 5.1, line 649). BUT Sec 5.2 adds a caveat the bare claim omits: goldfish supervises on fewer tokens, so reaching loss parity requires MORE input tokens ('20 billion supervised = 26.7 billion input tokens' at k=4, line 674) via extra steps or larger batch, and the authors state plainly 'this is not a free lunch' (line 690).
**Correction:** Reword to: 'reduces extractable verbatim memorization with only marginal downstream-benchmark impact AT SMALL k (k=3, k=4) — but it is not a free lunch: because only (1-1/k) of tokens are supervised, matching standard-loss validation loss requires feeding ~1/(1-1/k)x more input tokens (more steps or larger batch). At k=4 that is +33% input tokens.' Also scope it: results are 1B-7B params, 20B tokens, English; downstream parity at large k (the paper goes up to k=128) is not claimed.

**Claim:** Does the paper support k=h=50 specifically as a reasonable setting?
**Verdict:** `UNSUPPORTED`
**Evidence:** The paper never tests, mentions, or recommends k=50 or h=50. The k sweep is {3, 4, 8, 12, 32, 128} (Figs 3/5/7/8; e.g. 'Static 32-GL / Static 128-GL', lines 529-530). The h values are h=7 (a NEGATIVE example of too-small, line 346), h=13 (recommended, tied to the 13-gram contamination convention, lines 393-395), and Hash h=4 / Hash h=13 in experiments (lines 1214-1216). Every literal '50' in the text refers to epochs/repetitions ('repeat this target set 50 times', line 444; '50 epochs', line 460) or axis percentages, never to k or h. k and h are also distinct knobs (k=drop frequency, h=hash context width), so 'k=h=50' conflates two parameters the paper keeps separate.
**Correction:** Drop the citation as support for k=h=50. The paper supports neither value. If the project wants a defensible goldfish setting grounded in THIS paper, cite its actual recommendations: a low drop frequency (k=3 or k=4, the validated benchmark-neutral regime) and a hash context width of h=13 (the recommended setting, motivated by 13-gram contamination overlap). If a larger k is desired, the paper only goes as far as k=32/k=128 (with degrading memorization safety and a larger token-overhead penalty) and explicitly leaves 'higher masking rates' to future work (line 943); k=50 would be an interpolation the paper does not validate.

## How we use it
Relevance to our Apertus-8B Greek CPT is real but bounded — treat goldfish loss as an OPTIONAL memorization-mitigation add-on, not a default for the Greek continued-pretraining run, and do not let CURRENT_HYPERPARAMETERS.md cite it for k=h=50 (the paper supports neither value). Concrete guidance to adopt: (1) If we enable it, use the paper's validated regime — small drop frequency k=3 or k=4 and hash context width h=13 (NOT 50) — since that is where 'marginal downstream impact' is actually demonstrated. (2) Budget the token overhead explicitly: at k=4 we must feed ~33% more input tokens to hit the same validation loss ((1-1/k)*input = supervised), and rescale world batch size by the same factor — this directly affects our compute plan and is the load-bearing caveat the abstract hides. (3) Validation is at 1B-7B / 20B tokens / English; for an 8B Greek run at larger scale the memorization/utility tradeoff is an open question the authors flag, so any claim of 'safe + free' is unwarranted. (4) The conclusion's note that goldfish can be applied selectively (high-risk/duplicated sources, late curriculum) is the most practical framing for us — apply it to known-sensitive or heavily-duplicated Greek sources rather than uniformly, to cap the utility cost. (5) Hashing must normalize text before hashing (soft dashes, NBSP) — note this interacts with our cleaning/normalization scope decisions.
